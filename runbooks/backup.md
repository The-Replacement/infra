# Runbook: backup

**Goal:** keep the state that is not in git and not regenerable, in one
encrypted repository that is verified after every write and restorable on
demand.

**Applies to:** the workstation (control plane) and `mainframe` (radio runtime).
**Last exercised:** never end to end. Phase 1 backs up and verifies a synthetic
tree; the first real run is the first real run (see `restore-drill.md`).

## What is backed up, and why

There is exactly one rule: **if it cannot be rebuilt from git and seeds, it is
state and it is backed up; if it can be rebuilt, its absence from the backup is
the point.**

| Source | What it is | Why it is not in git |
|---|---|---|
| `<projects>/*/.n3rv` | engineering memory, exec cache, hub state, per-project a2a config | local to the workstation, written by agents |
| OpenCode database | sessions, messages, tool-output index | 1 GB SQLite, machine state |
| mainframe `.env`, `secrets/`, `config/`, `caddy/tokens.caddy` | listener tokens, Icecast passwords, feeds, the generated auth matcher | **secrets** |
| mainframe `data/indiegen/` (minus `runs/`) | `state.json` seed cursor, restart signal | runtime, written by the generator |
| XERJ data directory | indexes **and** the auth/idp/token state beside them | index is rebuildable, the auth state is not |

Deliberately excluded: `music-audio/`, `music/`, `data/host/`, `data/cam/`
(regenerated by indiegenerator and Mario), Docker images and build caches,
`runs/` (1.8 GB of render history), logs, `.venv`, `node_modules`.
Reasoning: `The-Replacement/docs/autonomy/04-disposability.md`.

The mainframe path is pulled over SSH in a single round trip and staged
locally. The mainframe never needs restic, and nothing is written on it.

## One-time setup

On the workstation, once:

```bash
install -d -m 700 ~/.config/radio-backup

# The password. Store a copy in the password manager BEFORE the first backup:
# without it the repository is random bytes, by design.
install -m 600 /dev/null ~/.config/radio-backup/restic-password
openssl rand -base64 32 > ~/.config/radio-backup/restic-password

install -m 600 /dev/null ~/.config/radio-backup/backup.conf
$EDITOR ~/.config/radio-backup/backup.conf     # from deploy/backup.conf.example
```

Create the repository **once**, with the password file already in place. The
script refuses to do this itself: a typo in `RESTIC_REPOSITORY` would otherwise
create a new empty repository and look like a successful backup.

```bash
set -a; . ~/.config/radio-backup/backup.conf; set +a
restic -r "$RESTIC_REPOSITORY" --password-file "$RESTIC_PASSWORD_FILE" init
```

Check what the script thinks it will do before it does it:

```bash
./deploy/backup.sh plan
```

`plan` reads no repository and writes nothing. It prints the sources, the
staging layout, the retention policy, and pings the mainframe to confirm the
expected files exist there.

## Run

```bash
./deploy/backup.sh backup
```

In order, it:

1. takes an exclusive lock (`flock` on `$STAGE_DIR/.backup.lock`);
2. stages every source into `$STAGE_DIR/run-<timestamp>/`, excluding the
   regenerable paths above;
3. copies each SQLite file with the SQLite backup API and runs
   `PRAGMA quick_check` on the copy — a live `cp` of a WAL database is a torn
   file, and a torn backup is not a backup;
4. runs `restic backup` with the `radio-state` tag and the workstation hostname;
5. runs `restic check --read-data-subset=$VERIFY_SUBSET`;
6. applies retention (`forget` + `prune`) to the tagged snapshots;
7. prints the snapshot ID and removes the staging tree.

Success looks like a snapshot line and `no errors were found` from `check`.
Anything else is a failure: read the last lines of
`~/.local/state/radio-backup/backup.log`. On failure the staging tree is kept
and its path printed, so the file that broke it can be inspected.

### Optional: nightly timer

Host-local units are not committed, because nothing in this repository is
deployed automatically. If you want a schedule, install a user unit that runs:

```bash
ExecStart=%h/Repositories/infra/deploy/backup.sh backup
```

with `OnCalendar=*-*-* 03:15:00` and `Persistent=true`, the same shape as the
existing `backup-to-usb` units. Start it by hand once first: a timer that has
never fired is a guess.

## Inspect and verify

```bash
./deploy/backup.sh snapshots        # what exists, and how big each snapshot is
./deploy/backup.sh check            # metadata + 1/50 of the data
./deploy/backup.sh restore-dry-run  # every path a restore would write
```

`restore-dry-run` takes a snapshot ID or `latest`. It reads the tree, prints the
mapping from the staged path back to the live path, and runs
`restic restore --dry-run`. It writes nothing.

A full data read belongs in the monthly drill, not in the nightly job:

```bash
restic -r "$RESTIC_REPOSITORY" --password-file "$RESTIC_PASSWORD_FILE" \
  check --read-data
```

## When it fails

| Symptom | Meaning | Action |
|---|---|---|
| `cannot read the repository` | uninitialised, wrong path, or wrong password | do **not** init over it; find the right repository first |
| `RESTIC_PASSWORD_FILE mode is 644` | the password is readable by others | `chmod 600`, then rotate the repository password |
| `another backup holds the lock` | a run is in progress, or a crashed one left the lock | confirm no restic process is running; the lock is released when its holder exits |
| `OpenCode database not found` | the configured path is wrong, or the install moved | fix `OPENCODE_DATA_DIR`, or unset it to skip on purpose |
| mainframe staging fails | SSH is down, or `.env`/`secrets/` is missing there | fix the host or the config; a partial radio backup is worse than a loud failure |
| `staging produced no files` | every source was empty or unset | fix the config; the script will not write an empty snapshot |

**Losing the password loses the repository.** There is no recovery path and
adding one would defeat the encryption. Keep the password in the password
manager and test the restore drill before you need it.

## Known gaps

- The XERJ index and the Chroma segment files inside `.n3rv/memory` are copied
  while their services run. The SQLite files are consistent; the binary segment
  files are only crash-consistent. Quiescing the services (`n3rv`, `xerj`, the
  OpenCode service) before a backup makes it fully consistent; the drill checks
  detect when that mattered.
- The staging tree needs roughly the size of the OpenCode database free (~1 GB
  today) on the workstation.
- One repository, one location. There is no offsite copy yet; a fire or a
  stolen USB drive is still a total loss. Tracked separately from this change.
- `restic check --read-data-subset` samples; only the monthly drill reads
  everything.
